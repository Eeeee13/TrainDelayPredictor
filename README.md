# Предиктор изменений в графике движения городского транспорта

Приложение для диспетчера, которое принимает телеметрию транспорта, сопоставляет её с расписанием и прогнозирует отклонения на горизонте от 10 до 15 минут. На карте отображаются транспорт, история движения, уровни риска и предполагаемые причины задержек.

![Диспетчерский дашборд с картой транспорта и карточкой рейса](docs/images/dashboard.jpeg)

## Возможности

- Приём телеметрии NDTP по TCP и воспроизведение исторических CSV.
- Очистка GPS, сопоставление с расписанием, расчёт текущего отклонения, скорости и простоев.
- Прогноз величины отклонения и калиброванной вероятности опоздания более чем на две минуты.
- Карта, привязка транспорта к геометрии маршрутов, история движения, тепловая карта рисков, поиск и фильтры.
- Карточки инцидентов, обновления через WebSocket и браузерные уведомления.
- PDF-отчёты по рейсам с ИИ-анализом и рекомендациями при настроенном доступе к Yandex Cloud.
- Автоматическое переобучение через Airflow, проверка качества, версионирование и откат моделей.

## Архитектура

Три основных модуля запускаются отдельными Docker-контейнерами.

| Модуль | Назначение |
| --- | --- |
| Backend, FastAPI | Приём телеметрии, сопоставление с расписанием, планирование прогнозов, API и WebSocket |
| ML, LightGBM | Прогноз отклонения и вероятности задержки |
| Frontend, React | Диспетчерская карта и карточки транспорта |

PostgreSQL хранит данные, Redis Streams передаёт события, Airflow управляет переобучением. ML-сервис читает PostgreSQL через роль с правами только на чтение.

## Подготовка

Понадобятся Git, Docker с Docker Compose и распакованный датасет организаторов. Команды ниже выполняются из корня репозитория в Bash или Zsh.

```bash
git clone https://github.com/Eeeee13/TrainDelayPredictor.git
cd TrainDelayPredictor
```

Укажите абсолютный путь к датасету. Внутри него должны находиться каталоги `train` и `test` с файлами `schedule.csv` и `traffic.csv`.

```text
dataset/
  train/
    schedule.csv
    traffic.csv
  test/
    schedule.csv
    traffic.csv
```

```bash
export DATASET_PATH="/absolute/path/to/dataset"
```

Замените путь на свой. Переменную нужно задавать в каждом новом терминале, из которого выполняется Docker Compose. Альтернатива: добавить `DATASET_PATH=/absolute/path/to/dataset` в файл `.env` в корне проекта. По умолчанию используется каталог `./dataset`.

## Запуск через Docker Compose

```bash
docker compose up -d --build
docker compose ps
curl --fail http://localhost:8000/health/ready
```

Дождитесь ответа `{"status":"ready","database":"ok"}`. При первом запуске сборка образов и установка зависимостей могут занять несколько минут.

| Что открыть | Адрес |
| --- | --- |
| Диспетчерский дашборд | http://localhost |
| Swagger Backend | http://localhost:8000/docs |
| ReDoc Backend | http://localhost:8000/redoc |
| OpenAPI Backend | http://localhost:8000/openapi.json |
| Последние риски и прогнозы | http://localhost:8000/risk |
| Снимок данных дашборда | http://localhost:8000/dashboard/snapshot |

Frontend публикуется на порту **80**, Backend на **8000**, приёмник NDTP на **9201**. PostgreSQL, Redis, ML и Airflow доступны внутри Docker-сети. Порты ML и веб-интерфейса Airflow в текущем Compose на хост не опубликованы.

Проверить ML и активную версию модели можно из контейнера Backend.

```bash
docker compose exec backend python -c "import httpx; print(httpx.get('http://inference:8000/health').json()); print(httpx.get('http://inference:8000/model/info').json())"
```

Посмотреть логи:

```bash
docker compose logs --tail=100 backend inference frontend
docker compose logs --tail=100 airflow
```

До подачи телеметрии карта может быть пустой. Для демонстрации прогнозов используйте CSV replay ниже.

## CSV replay с 06:00 на скорости 10

В отдельном терминале из корня проекта запустите:

```bash
docker compose exec backend python -m scripts.replay_csv \
  --schedule /dataset/train/schedule.csv \
  --traffic /dataset/train/traffic.csv \
  --backend http://localhost:8000 \
  --start-at 2026-01-06T06:00:00 \
  --speed 10 \
  --pause-at-end
```

Дата в команде соответствует примеру исторических данных проекта. Если ваш CSV содержит другой день, замените `2026-01-06`, сохранив время `06:00:00`. Время CSV интерпретируется как московское. Воспроизведение начинается с первой доступной записи не раньше указанного времени.

Скрипт сначала загружает расписание, затем устанавливает виртуальные часы Backend и отправляет телеметрию. Скорость `10` означает десять секунд истории за одну реальную секунду. Даты истории сохраняются. Параметр `--pause-at-end` останавливает виртуальные часы после завершения, чтобы итоговую карту можно было изучить.

Откройте http://localhost и дождитесь загрузки расписания и первых пакетов. Прогнозы появляются для остановок, плановое прибытие на которые находится в окне от 10 до 15 минут относительно виртуального времени.

Дополнительные параметры:

- `--end-at 2026-01-06T08:00:00` ограничивает демонстрацию двумя часами истории.
- `--vehicle 133300` воспроизводит только выбранный `tr_id`.
- `--metrics-output /tmp/replay-metrics.json` сохраняет длительности запросов и фактическую скорость replay внутри контейнера.

Остановить отправку можно через `Ctrl+C`. После досрочной остановки виртуальные часы сами не замораживаются. Чтобы зафиксировать текущий момент:

```bash
curl --fail -X POST http://localhost:8000/ingest/replay-clock/pause
```

Перед переходом к живому эмулятору завершите CSV replay и верните Backend к текущему времени:

```bash
curl --fail -X POST http://localhost:8000/ingest/replay-clock/resume-live
```

Не запускайте CSV replay и живой поток одновременно: у них разные временные шкалы.

## Запуск эмулятора NDTP

Эмулятор поставляется организаторами отдельным Docker-архивом. Команды ниже используют образ `ndtp-telemetry-emulator:1.0` из приложенной инструкции.

### 1. Загрузить образ

Замените путь на расположение архива:

```bash
docker load -i /absolute/path/to/ndtp-telemetry-emulator.tar
```

### 2. Настроить соответствие устройств и транспорта

`unitId` обозначает устройство эмулятора, `tr_id` обозначает транспортное средство в датасете. Установите соответствия:

```bash
curl --fail -X POST http://localhost:8000/ndtp-mapping \
  -H 'Content-Type: application/json' \
  -d '{"664030":115106,"794446":116057,"663271":116445}'

curl --fail http://localhost:8000/ndtp-mapping

docker compose restart backend
```

Перезапуск обязателен: TCP-приёмник читает маппинг из Redis при старте. Дождитесь готовности Backend и включите текущее время:

```bash
curl --fail http://localhost:8000/health/ready
curl --fail -X POST http://localhost:8000/ingest/replay-clock/resume-live
```

### 3. Подготовить конфигурацию

В репозитории есть [пример конфигурации](emulator_sample_config.json). Он содержит десять устройств. Для приведённого выше маппинга создайте конфигурацию только с тремя соответствующими устройствами:

```bash
cat > /tmp/ndtp-emulator-config.json <<'JSON'
{
  "targetHost": "host.docker.internal",
  "targetPort": 9201,
  "units": [
    {"unitId": 664030, "intervalMs": 5000, "autoGenerate": true, "cells": []},
    {"unitId": 794446, "intervalMs": 5000, "autoGenerate": true, "cells": []},
    {"unitId": 663271, "intervalMs": 5000, "autoGenerate": true, "cells": []}
  ]
}
JSON
```

Чтобы использовать все устройства из `emulator_sample_config.json`, предварительно добавьте в маппинг корректный `tr_id` для каждого `unitId`. Пакеты неизвестных устройств Backend пропускает.

### 4. Запустить и настроить эмулятор

```bash
docker run -d --rm \
  --name ndtp-emu \
  -p 18080:18080 \
  --add-host=host.docker.internal:host-gateway \
  ndtp-telemetry-emulator:1.0

curl --fail -X POST http://localhost:18080/api/config \
  -H 'Content-Type: application/json' \
  --data-binary @/tmp/ndtp-emulator-config.json
```

`host.docker.internal` позволяет эмулятору подключиться к опубликованному TCP-порту Backend. Если `docker load` сообщил другое имя или тег образа, используйте его в `docker run`.

### 5. Проверить приём данных

```bash
docker logs --tail=100 ndtp-emu
docker compose logs --tail=100 backend
curl --fail http://localhost:8000/dashboard/snapshot
```

Откройте http://localhost. При `autoGenerate: true` эмулятор создаёт случайное движение около Москвы. Такой режим демонстрирует приём телеметрии и отображение транспорта. Для осмысленного ML-прогноза нужны расписание на текущую дату, целевые остановки в ближайшие 10–15 минут и движение вдоль соответствующего маршрута. Историческое расписание после CSV replay само на текущую дату не переносится. Расписание можно загрузить через `POST /ingest/schedule` по схеме в Swagger.

Для демонстрации полного пути от реального расписания до прогноза используйте CSV replay.

Остановить эмулятор:

```bash
docker stop ndtp-emu
```

Маппинг хранится в Redis. После пересоздания Redis задайте его повторно и перезапустите Backend.

## Где смотреть прогнозы, алерты и метрики

- **Карта** открывается по умолчанию. Выберите транспорт на карте или в списке слева.
- **Карточка справа** показывает фактическое отклонение, прогноз, вероятность задержки, проблемный участок, последнюю телеметрию и ближайшие остановки.
- **Вкладка «Алерты» слева** помогает найти проблемный транспорт. Для системных уведомлений включите их в интерфейсе и разрешите браузеру показывать уведомления.
- **Верхняя панель** показывает долю транспорта по графику, долю в риске и среднее отклонение.
- **Кнопка «Сгенерировать отчёт»** в карточке скачивает PDF с метриками рейса, графиками и ИИ-разбором при настроенном Yandex Cloud.

Вероятность относится к событию «опоздание более 120 секунд». Если классификатор недоступен или используется резервный прогноз, вероятность не показывается.

### Настройка PDF-отчётов

Добавьте в `.env` в корне проекта параметры своего Yandex Cloud:

```dotenv
YANDEX_CLOUD_API_KEY=your_api_key
YANDEX_CLOUD_FOLDER=your_folder_id
YANDEX_CLOUD_MODEL=deepseek-v4-flash/latest
```

Примените настройки:

```bash
docker compose up -d backend
```

Для отчёта нужны накопленная телеметрия выбранного транспорта и доступ к указанной модели. Без ключа карта и прогнозы работают, но генерация ИИ-отчёта недоступна.

## Документация и API

Основные эндпоинты:

| Метод и путь | Назначение |
| --- | --- |
| `POST /ingest/telemetry` | Приём нормализованной телеметрии |
| `POST /ingest/schedule` | Загрузка расписания |
| `GET /dashboard/snapshot` | Данные дашборда |
| `GET /risk` | Последние риски по транспорту |
| `GET /risk/{vehicle_id}` | Риск выбранного транспорта |
| `GET /vehicles/{vehicle_id}/deviation` | Текущее отклонение от расписания |
| `POST /vehicles/{vehicle_id}/report` | PDF-отчёт по рейсу |
| `POST /risk/recompute` | Принудительная проверка прогнозного окна |
| `GET /ndtp-mapping` и `POST /ndtp-mapping` | Чтение и установка маппинга NDTP |
| `WS /ws/risk` | Обновления рисков в реальном времени |

## Производительность и надёжность

В локальной проверке пакет из транспортных средств обрабатывался за 1,552 секунды при первом HTTP-запросе и за 0,519 и 0,481 секунды при следующих. Это результат конкретного пакета, а не полноценного нагрузочного теста. Для повторных замеров предусмотрен `backend/scripts/benchmark_inference.py`.

Используются кеширование расписания и состояния, пакетный инференс и событийная очередь. При ошибке или таймауте ML резервный прогноз равен текущему отклонению. При недоступности Redis на старте событийная шина может перейти на внутреннюю очередь. При обрыве телеметрии сохраняется последнее известное состояние, а устаревший транспорт исключается из активного календаря прогнозов.

Первый прогноз создаётся только в окне `(10, 15]` минут до плановой остановки. Для высокого риска предусмотрены повторные проверки в том же окне. Прогнозы задним числом не создаются.

## Переобучение и версии моделей

Airflow запускает DAG `delay_retraining` каждые пять минут. Исторические данные для обучения открываются постепенно, с отдельной скоростью `TRAIN_REPLAY_SPEED=6`. Она не связана со скоростью CSV replay на дашборде.

Кандидат публикуется при улучшении MAE и отсутствии ухудшения Brier score относительно активной модели. Встроенная конкурсная модель уже обучалась на `test`, поэтому это техническая проверка перед заменой, а не независимая оценка качества. Новый комплект модели и калибратора активируется атомарно и подхватывается при следующем запросе. При ошибке загрузки сохраняется предыдущая версия.

Откат к существующей версии:

```bash
docker compose exec airflow python -m ml_pipeline.rollback VERSION
```

Замените `VERSION` идентификатором сохранённой версии в volume `models`.

## Остановка

```bash
docker compose down
```

Команда останавливает сервисы и сохраняет именованные тома с базой и моделями. Для повторного запуска выполните `docker compose up -d`.

## Если что-то не работает

- Пустая карта после старта: подайте CSV или NDTP и проверьте `/dashboard/snapshot`.
- Нет прогнозов: проверьте временную шкалу, наличие расписания и остановок в прогнозном окне.
- Ошибка `unmapped NDTP unit_id`: добавьте устройство в маппинг и перезапустите Backend.
- CSV не найден: проверьте `DATASET_PATH` и наличие `/dataset/train/traffic.csv` внутри контейнера.
- Порт 80 занят: освободите его или замените у `frontend` публикацию `80:80` на `3000:80`, после чего открывайте http://localhost:3000.
- PDF не формируется: проверьте настройки Yandex Cloud и логи Backend.
